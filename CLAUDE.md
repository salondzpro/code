Monorepo pnpm : `apps/api` (Fastify), `apps/web` (Vite/React), `apps/mobile` (Expo), `packages/*` (constants, types, validation, api-client), `supabase/migrations`.

## Commandes
- `pnpm install` · `pnpm typecheck` · `pnpm --filter @salondz/validation test` · `pnpm --filter @salondz/api test` (e2e réel contre Supabase, crée puis supprime des utilisateurs jetables)
- `pnpm --filter @salondz/web test:e2e` : parcours complet pro + client dans Chromium headless (playwright-core) ; exige `pnpm dev:api` (8090) + `pnpm dev:web` (9000) lancés, `PLAYWRIGHT_CHROME` si Chrome n'est pas installé. Captures dans `apps/web/test/shots/`. **Le contexte pro tourne à 1 280 px, donc sur l'affichage ORDINATEUR** (rail permanent) : un libellé présent à la fois dans le rail et dans le contenu doit être visé via `.pro-main`. Ce scénario dérive vite du produit (libellés, étapes) : quand il échoue, ouvrir d'abord la capture `*-FAIL-*` — elle montre où l'on est réellement — avant de conclure à une régression ; le message d'échec donne aussi la ligne « waiting for … » de Playwright, qui dit ce qui était attendu. **Mémoire** : le navigateur ouvre trois contextes et prend des captures pleine page ; sur cette machine (8 Go), un passage complet demande de fermer VS Code ou JetBrains Toolbox, sinon il est tué en cours de route — ce n'est pas un échec du scénario.
- `pnpm test:e2e:mobile` : parcours client + pro sur l'app mobile rendue par Expo web (`apps/mobile/test/smoke.e2e.mjs`) ; exige `pnpm dev:api` et, depuis `apps/mobile`, `CI=1 EXPO_PUBLIC_API_URL=http://localhost:8090 npx expo start --web --port 8082`. Captures dans `apps/mobile/test/shots/`.
- `node --env-file=.env scripts/test-cleanup.mjs` : liste les comptes `@salondz.test` laissés par les suites e2e et les salons qu'ils traînent ; `--yes` pour supprimer. **À lancer après tout passage e2e interrompu** : le nettoyage des scénarios vit dans un `finally`, qui ne s'exécute pas quand le processus est TUÉ (mémoire) — onze salons de test s'étaient ainsi retrouvés PUBLIÉS sur la place de marché en production.
- `pnpm demo:seed` / `pnpm demo:cleanup` : deux salons de démonstration (Sarah Beauty Studio, Amine Barber) + une cliente avec rendez-vous, pour captures et tests manuels ; sessions dans `scripts/.demo.json` (gitignoré). Exige `pnpm dev:api`.
- `pnpm check:realtime` : rejoue contre la **prod** le scénario « le pro est sur son accueil, la cliente réserve » et dit si l'événement Realtime arrive sans actualiser (`scripts/check-realtime.mjs`, comptes de démonstration, rendez-vous de test annulé à la fin). À lancer après toute modification du temps réel ou de la publication Postgres.
- `pnpm check:contact` : ouvre les écrans clients en **prod** et vérifie qu'aucun numéro, appel ou WhatsApp du salon n'y apparaît (drapeau `SHOW_SALON_CONTACT_TO_CLIENTS`).
- `pnpm check:for-other` : réservation POUR QUELQU'UN D'AUTRE contre la **prod** — le rendez-vous atterrit sur le compte de la personne quand son numéro en a un, sinon sur son numéro seul ; qui a réservé est conservé ; celui qui a réservé le retrouve dans ses rendez-vous ; les règles restent celles de la personne concernée. Nettoyage par annulation DU SALON (une annulation cliente compterait dans l'anti-abus).
- `pnpm check:badge` : pastille rouge des demandes à confirmer sur l'onglet Réservations, contre la **prod** — apparition sans actualiser (temps réel), compte qui suit, baisse après confirmation, visible depuis les autres écrans pro. Coupe la confirmation automatique du salon de démo et **la remet dans tous les cas** (`finally`).
- `pnpm check:control` : contre la **prod**, un administrateur ENTRE dans l'espace d'un professionnel avec un jeton daté et le BLOQUE (gelé, masqué, levé ; client suspendu ; jeton personnel, falsifié, coupé par le retrait d'accès). Trois comptes et un salon jetables (`@salondz.test`), nettoyés dans un `finally`. À lancer après toute modification de `plugins/auth.ts`, de `lib/control.ts` ou des routes `/pro/salon`.
- `pnpm check:webpush` : chaîne complète des notifications navigateur en **prod**. Le dernier saut exige une fenêtre réelle : `CHECK_HEADLESS=0 pnpm check:webpush`. Sans affichage, Chrome fait juger son inscription FCM périmée (410) — ce n'est pas une régression.
- Traduction : `node scripts/i18n-codemod.mjs` (enveloppe les textes JSX dans `t()`), `node scripts/i18n-keys.mjs` (extrait les clés vers `apps/web/src/i18n/keys.json`).
- `pnpm db:backup` : pg_dump gratuit (schémas `public` + `auth`) dans `backups/` (hors git) — à lancer AVANT chaque migration tant que Supabase Pro est reporté (décision du 18 sept. 2026).
- `pnpm db:migrate` (lit `DATABASE_URL` dans `.env`, suit `public.schema_migrations`). Les migrations déjà appliquées sont immuables : toute correction = nouveau fichier `000N_*.sql`.
- API locale : `pnpm dev:api` sur le port `PORT` du `.env` (8090 en local, 8080 sur Render) ; web toujours sur http://localhost:9000 (Vite `strictPort`).

## Règles métier non négociables
- Devise DA uniquement (`formatDA`), jamais d'euros. Fuseau `Africa/Algiers`. Semaine **dimanche → samedi** (`WEEK_STARTS_ON = 0`, `weekKeys()`), `day_of_week` 0 = dimanche.
- Anti-double réservation = contrainte d'exclusion GiST sur `bookings` + fonctions SQL `create_booking` / `reschedule_booking` / `get_available_slots`. Ne jamais réimplémenter la logique de créneaux côté API/front ; Realtime = affichage seulement.
- Règles du salon appliquées en SQL (`create_booking_multi`, `reschedule_booking` avec `p_enforce_rules`) : délai minimum, horizon, annulation/report jusqu'à `cancel_min_hours`, report client désactivable (`allow_client_reschedule`). Les fonctions d'écriture sont révoquées pour `anon`/`authenticated` (migration 0009) : seule l'API (clé secrète) les appelle.
- **Plusieurs prestations = UN rendez-vous**, côté client comme côté pro : `create_booking_multi` écrit une réservation et ses `booking_items` (durée et prix cumulés, nom composé). L'écran pro laissait cocher plusieurs prestations mais créait autant de rendez-vous à la suite — plusieurs blocs dans l'agenda pour une seule venue, autant de lignes dans l'historique du client, et un rendez-vous coupé en deux si la deuxième création échouait. Ne jamais revenir à une boucle de création : `createWalkInBookingSchema` prend `serviceIds`.
- **Réservation POUR QUELQU'UN D'AUTRE** (`beneficiary` dans `createBookingSchema`) : le rendez-vous appartient à la PERSONNE CONCERNÉE, jamais à celle qui réserve. Son numéro l'identifie : s'il correspond à un compte, `client_id` est celui-là ; sinon `client_id` reste nul et le numéro seul l'identifie. Les règles se lisent donc sur elle, par compte ET par numéro (`clientFilter` / `clientStanding` dans `apps/api/src/lib/standing.ts`). `booked_by` / `booked_by_name` gardent qui a réservé : cette personne garde l'accès (voir, annuler, reporter) mais pas l'avis, qui reste à la personne concernée. Vérifié par `pnpm check:for-other`.
- **Validation manuelle et liste d'attente (16 sept. 2026, façon Planity)** : une demande `pending` BLOQUE le créneau pour les autres (exclusion GiST + `get_available_slots_for`) ; le pro est relancé après `PENDING_REMINDER_HOURS` (notification `request_pending`) et la demande expire après `PENDING_REQUEST_TTL_HOURS` ou à l'heure du rendez-vous (cron, `cancelled_by = 'system'`, client prévenu). Tout créneau libéré (annulation client ou pro, report, expiration, blocage retiré) passe par `lib/waitlist.ts` → `notifySlotFreed` : notification `slot_freed` (in-app + push, `data.url` vers `/s/:slug/prestations?date=`) aux inscrits de `slot_alerts` (un client, un salon, un jour ; `POST/GET/DELETE /v1/me/slot-alerts`, bouton « M'alerter si un créneau se libère » sur le jour complet) puis aux clients ayant rendez-vous PLUS TARD dans ce salon, les plus éloignés d'abord, même prestation si connue (`SLOT_FREED_MAX_LATER_CLIENTS`). Premier arrivé, premier servi : la notification mène à la réservation, elle ne réserve pas. Ne jamais rendre `notifySlotFreed` bloquant.
- **Réglages de notification du client** : « Rappels » (`reminders_enabled`, migration 0041 ; la veille `reminder_sent_at` ET 2 h avant `reminder_2h_sent_at`, remis à zéro par le déclencheur quand le rendez-vous bouge ; lus par le cron) et « Confirmations » (`notify_confirmations`, migration 0040 : réservation, confirmation, report, annulation restent dans l'app mais ne sont plus poussées ; `CONFIRMATION_TYPES` dans `lib/push.ts`, clients seulement — un pro reçoit toujours ses demandes). Pas d'interrupteur sans effet serveur : « Nouveautés » a été retiré tant qu'aucune fonctionnalité n'existe.
- **Rappel au professionnel (21 sept. 2026, migration 0046)** : une notification `PRO_REMINDER_LEAD_MINUTES` (60) min avant chaque rendez-vous CONFIRMÉ, au propriétaire du salon, une seule fois (`bookings.reminder_pro_sent_at`, remis à zéro par le déclencheur `reset_reminder_on_move` avec les deux rappels client quand le rendez-vous est déplacé). Étape 1c du cron, fenêtre 20–70 min avant le début. Un rendez-vous pris moins de 75 min avant son début est marqué traité SANS notification (le pro vient d'être prévenu par la réservation). Type `booking_reminder` PARTAGÉ avec le client : le pro se reconnaît à `data.audience = 'pro'` (l'application mobile s'en sert pour ouvrir la fiche côté pro). Pas d'interrupteur : `profiles.reminders_enabled` est le réglage du CLIENT et un pro n'a aucun écran pour le rallumer ; à ajouter si les pros se plaignent du volume. Vérifié en prod par `pnpm check:pro-reminder` (compte et salon jetables, horaires posés en base).
- **Canal des notifications (18 sept. 2026, client ET pro)** : jamais WhatsApp/SMS aujourd'hui. `lib/push.ts` envoie à l'application mobile (jeton Expo) si elle est installée, SINON au navigateur (Web Push) ; jamais les deux. Toujours visibles dans l'application (`notifications`). Un canal hors application (SMS/WhatsApp) reste une décision propriétaire (plan, décision 5).
- **Notifications purgées par le cron** (`/internal/cron/tick`, étape 5) : lues depuis plus de `NOTIFICATION_READ_TTL_DAYS` (7 j) ou créées depuis plus de `NOTIFICATION_MAX_AGE_DAYS` (30 j) → supprimées (index partiel `notifications_read_idx`, migration 0031). Une notification est une information du moment, pas une archive : ne jamais s'appuyer dessus comme historique.
- **Réponse du professionnel aux avis (19 sept. 2026, migration 0043)** : `reviews.reply` / `replied_at`, routes `GET /pro/reviews`, `GET /pro/reviews/unanswered`, `PUT /pro/reviews/:id/reply` (le filtre porte AUSSI sur `salon_id` : on ne répond jamais à l'avis d'un autre salon). La réponse est PUBLIQUE et unique ; répondre vide l'efface. Le professionnel répond, il ne corrige ni la note ni le texte — aucune route ne le permet, et l'écran ne le propose pas. Affichage public par `components/ReviewReply.tsx`, écran pro `pages/pro/ProReviews.tsx`.
- **Identité d'un client chez un salon (18 sept. 2026, migration 0042)** : une seule fiche par personne. La clé est le NUMÉRO — celui du compte quand il y en a un (donc à jour), sinon celui du rendez-vous — puis le compte, puis le nom (`public.client_key`, portée à l'identique dans `apps/web/src/demo/engine.ts` par `clientKeyOf`). Un client reçu de passage puis revenu avec un compte ne fait plus deux fiches, deux historiques et deux blocs de notes. Le blocage suit cette identité (`blocked_clients.client_key`) : un client de passage connu du seul salon est blocable, mais comme il ne peut pas réserver en ligne, ce blocage est un repère dans la clientèle — l'écran le dit. `create_booking_multi` continue de refuser sur `client_id` / `phone`, les seules identités qu'une réservation en ligne présente. `POST /pro/clients/block|unblock` prend `{ clientKey }` : le compte et le numéro sont retrouvés côté serveur, jamais déclarés par l'appelant.
- Garde-fous API (`packages/constants/src/booking.ts`) : au plus `MAX_UPCOMING_BOOKINGS_PER_CLIENT` rendez-vous à venir par client, pas de doublon du même client sur un horaire qui chevauche (`ALREADY_BOOKED`), plafonds équipe/catalogue, blocage ≤ 1 an. Transitions pro : `confirmed` impossible après l'heure (`BOOKING_EXPIRED`), `no_show` impossible avant l'heure (`NOT_STARTED`). Le cron (`/internal/cron/tick`) expire les demandes `pending` passées (`cancelled_by = 'system'`).
- Téléphones normalisés E.164 `+213…` via `phoneDZ` ; snake_case en base, camelCase dans l'API (`camelize`). Un numéro vérifié par OTP (dans le jeton) n'est pas modifiable via `PATCH /me` ; le lien (`slug`) du salon est définitif.
- **Trois langues sur le web (16 sept. 2026) : français, arabe (RTL) et anglais**, `apps/web/src/i18n/` (`t(fr, vars)` KEYÉ PAR LA PHRASE FRANÇAISE, dictionnaires `ar.ts` / `en.ts`, `useLocale`, `switchLocale` qui enregistre et recharge, `LOCALES`). Le code s'écrit en français puis passe par `t(...)` : nouveau texte = `node scripts/i18n-codemod.mjs` (enveloppe les chaînes JSX) puis `node scripts/i18n-keys.mjs` (liste `i18n/keys.json`) et une entrée par langue dans `ar.ts` / `en.ts`. Traduction dans le vocabulaire du métier (coiffure, salon, créneau), jamais littérale. Pas de fragments de phrase autour d'une variable : une clé complète avec `{n}` (`t('{n} rendez-vous', { n })`). `packages/constants` traduit via `tr()` / `formatLocale()` (`i18n.ts`, branché par `setTranslator`). Langue choisie stockée dans `profiles.locale` (`fr`/`ar`/`en`, migration 0034) et réglable dans Réglages (client) / Compte (pro) / écran d'intro (`LangSwitch`). Textes de l'API (erreurs, notifications, e-mails) encore en français. **RTL** : utilitaires logiques uniquement (`ms-`/`me-`/`ps-`/`pe-`/`start-`/`end-`/`text-start`/`border-s`), jamais `ml-`/`left-`/`text-left` (sauf centrage `left-1/2`) ; un prix, une durée, une plage horaire ou une adresse se place dans `dir="ltr"` (ou `dir="auto"`) pour ne pas être retourné en arabe.

## Cache HTTP (API publique)
- Listes/salons : `public, max-age=60, stale-while-revalidate=600` (4G : réponses instantanées en revisite). Chrome ressert la copie périmée et ne revalide qu'en arrière-plan : pour une ressource qui doit refléter immédiatement une écriture (avis, disponibilités), utiliser `public, no-cache` (ETag → 304). Le propriétaire reçoit toujours `private, no-cache`.

## Administration de la place de marché (lot 1 livré le 20 sept. 2026)
- Conception complète dans `docs/ADMIN.md` (section 11 = ce qui est livré). **Lot 1 = VOIR, rien d'autre** : aucune route n'écrit dans les données d'un salon ou d'un client. Suspendre, masquer un avis, annuler au nom de la plateforme = lot 2 ; ne pas les glisser dans le lot 1 « puisque l'écran est là ».
- Un administrateur est un compte normal (client ou pro) inscrit dans `platform_admins` (`level` `support` | `owner`, migration 0044) — pas un troisième `user_role`. `node --env-file=.env scripts/admin.mjs list | grant <e-mail> [support|owner] | revoke <e-mail>` ; **`revoke` pose `disabled_at`, ne supprime jamais la ligne** (le journal doit rester lisible après coup).
- Quatrième garde, dans la même chaîne que les autres : `requireAuth` → `requireProfile` → `requireAdmin` (→ `requireOwner`). `platform_admins` et `admin_audit` ont la RLS activée SANS politique et tous droits révoqués pour `anon`/`authenticated` : seule l'API les lit. Tout refus part dans les journaux (compte, IP, route).
- **Adresse du portail : `admin.salondz.com`** (`ADMIN_HOST` dans `apps/web/src/lib/env.ts`). Elle sert la MÊME application : `main.tsx` réécrit la racine en `/admin` avant le démarrage du routeur (pas de rechargement), les liens profonds sont laissés tels quels, et `salondz.com/admin` continue de marcher. **Le sous-domaine n'est pas encore branché** : Render limite le plan gratuit à 2 domaines personnalisés PAR COMPTE (déjà salondz.com, www, api) — il faut soit un moyen de paiement sur Render, soit une redirection de sous-domaine côté IONOS vers `https://salondz.com/admin`. L'origine est déjà dans `CORS_ORIGINS` de l'API.
- `/v1/admin/*` : 120 requêtes/minute et par compte (plus serré que la limite générale), `Cache-Control: private, no-store` sur toutes les réponses.
- **La consultation d'une fiche NOMINATIVE (un salon, un compte) écrit dans `admin_audit` ; une liste ou un compteur, non.** Un journal qui enregistre tout ne se lit plus. L'écriture du journal n'est jamais bloquante : une erreur se signale et le travail continue.
- **Agir (lot 2, 21 sept. 2026, migration 0045)** — trois leviers, et UN SEUL vocabulaire :
  - **Suspendre un salon, à deux degrés** : `frozen` gèle les réservations (la page reste en ligne), `hidden` retire le salon de la place de marché. **`is_published` n'est JAMAIS touché** : c'est l'intention du professionnel. La colonne calculée `salons.is_visible` croise les deux, et c'est ELLE que la recherche publique interroge (`search_salons_v2`, `salon_cities`, `search_suggest`) — un levier oublié quelque part se voit tout de suite.
  - **Suspendre un client** (`profiles.suspended_at`) : plus de réservation EN LIGNE nulle part. Reçu en personne au salon, il reste l'affaire du salon — d'où la place du test, sous `p_enforce_rules` dans `create_booking_multi`. À ne pas confondre avec `blocked_clients`, qui est propre à UN salon.
  - **Masquer un avis** (`reviews.hidden_at`) : il quitte la page publique ET le calcul de la note (`reviews_refresh_rating`), sans être supprimé.
  - **Une suspension arrête ce qui ENTRE, jamais ce qui est déjà pris** : création et report refusés (`SALON_SUSPENDED`, `CLIENT_SUSPENDED`), mais confirmer, terminer ou annuler un rendez-vous existant reste possible — sinon on laisserait des clients devant une porte close sans prévenir personne.
  - **Annuler au nom de la plateforme** : `cancelled_by = 'platform'` (nouvelle valeur d'énumération), les deux parties prévenues, le créneau repart en liste d'attente.
  - **Motif obligatoire (8 caractères minimum) sur toute action**, et une ligne au journal. Le motif est montré À LA PERSONNE CONCERNÉE (bandeau pro et client, `components/SuspensionNotice.tsx`) : une plateforme qui coupe sans dire pourquoi n'est pas un partenaire.
  - **Rien ne se supprime** : on suspend, on masque, on rétablit. Seule exception, `DELETE /v1/admin/profiles/:id`, niveau `owner`, qui réutilise l'effacement de `DELETE /v1/me` (`lib/moderation.ts`) — rendez-vous passés anonymisés, pas supprimés.
- **Agir EN TANT QUE professionnel (lot 2)** : le bouton « Ouvrir son espace » (liste ET fiche des professionnels) appelle `POST /v1/admin/salons/:id/control`, qui délivre un **JETON DE CONTRÔLE** (`apps/api/src/lib/control.ts`) : JWT HS256 signé par une clé dérivée du secret serveur, **lié à l'administrateur (`sub`) ET au salon, valable 2 h** (`CONTROL_TTL_SECONDS`). Le web l'envoie dans `X-Admin-Control` aux seules routes `/v1/pro/*` et l'API le revérifie À CHAQUE requête (`resolveActing` dans `plugins/auth.ts`) : signature, échéance, `sub` = l'auteur de la requête, ET `requireAdmin` (retirer l'accès d'un administrateur coupe ses jetons en cours, rien à révoquer). Un jeton volé sans la session ne sert à rien, et l'inverse. Erreurs en **403** (`CONTROL_EXPIRED`, `CONTROL_INVALID`), jamais 401 : un 401 déconnecterait l'administrateur de sa propre session. C'est ce qui permet de dépanner un pro au téléphone au lieu de lui dicter des clics.
  - **Toute route `/pro/*` qui lit « le salon de l'appelant » doit passer par `requireSalon` ou `app.resolveActing`**, jamais par `loadOwnedSalon(req.user.id)` seul : c'est ainsi que `GET /pro/salon` ignorait le pilotage et renvoyait l'administrateur vers l'inscription d'un salon (corrigé le 21 sept.). En pilotage, `GET /pro/salon` ajoute `owner` (identité du professionnel) ; `POST /pro/salon` répond 409 (jamais de salon créé au nom de l'administrateur). L'espace pro affiche alors l'identité du PRO (accueil, Compte) et n'inscrit pas le navigateur de l'administrateur à ses notifications ; l'identité se corrige dans l'administration (`/admin/comptes/:id`, avec motif), pas via `PATCH /me`.
  - **Le pouvoir se paie** : l'entrée (`salon_control_start`) et la sortie (`salon_control_end`) sont au journal, un crochet `onResponse` écrit CHAQUE écriture faite à la place du pro (`acted_as_salon`), et un bandeau noir permanent (`components/ActingAsBanner.tsx`) rappelle chez qui l'on travaille et jusqu'à quelle heure ; à l'échéance il referme l'espace tout seul. Web : `lib/actingAs.ts` retient le jeton (localStorage, jeton périmé ignoré) ; entrer et sortir VIDE le cache de requêtes (`qc.clear()`) — le cache appartient au contexte qu'on quitte. Pas de temps réel en pilotage (la RLS de Realtime ne connaît pas l'administrateur) : les données se rechargent à la navigation.
  - **`SALON_SUSPENDED` et `CLIENT_SUSPENDED` sont mappés dans `lib/errors.ts`** (409 / 403) : levés par la base, sans cette entrée ils sortaient en 500 « Erreur base de données ». Tout nouveau code métier levé en SQL doit y figurer.
  - Vérifié en prod par `pnpm check:control` (administrateur, pro et salon jetables, nettoyés dans un `finally`) ; le test e2e 38 de l'API couvre la même chose.
- Écrans sous `/admin` (`apps/web/src/pages/admin/`), chargés à la demande. **Aucun lien n'y mène depuis l'application** : l'adresse se tape, le garde serveur est la seule barrière. Visiteur NON connecté → écran de connexion avec retour sur `/admin` (cela n'apprend rien : `/rendez-vous`, `/favoris` et l'espace pro demandent aussi de se connecter) ; connecté mais PAS administrateur (403) → accueil SANS message, et c'est le cas qui compte — on n'apprend pas à un client curieux qu'une porte existe. `WelcomeBack` n'envoie pas vers `/profil/creer` ni `/marche` quand la destination est `/admin` : le nom, le numéro et le marché servent à RÉSERVER, et un administrateur ne réserve rien. Écrans en lecture seule, et la fiche d'un salon le dit à l'écran : le catalogue, les prix et les horaires appartiennent au professionnel, en cas d'erreur on l'appelle.

## Sécurité
- **Durcissement du 16 sept. 2026** (audits, détail dans `docs/PRODUCTION.md`) : `API_PUBLIC_URL` obligatoire en production (jamais l'en-tête Host pour un lien e-mail) ; `TEST_LOGIN_ENABLED` désactivé sauf `1` explicite ; un seul mandataire de confiance (`trustProxy` premier saut) ; limitation de débit après l'authentification, par compte puis par IP, et par « e-mail + IP » sur les envois ; réponses 204 uniformes sur lien de connexion / renvoi / réinitialisation (pas d'oracle d'existence) ; `auth_user_by_email` (SQL, clé secrète) au lieu de `listUsers` ; journaux sans jeton ni chaîne de requête ni adresse complète ; URL d'images limitées au stockage Supabase (`p.httpUrl`) ; nom du titulaire d'un numéro jamais renvoyé, `MAX_FOR_OTHER_PER_DAY` ; `GET /v1/me/export` et `DELETE /v1/me` (anonymisation des rendez-vous passés, `HAS_SALON` pour un pro). Jeton cron : 32+ caractères, identique dans Render et `app_settings.cron_token`.
- **Schémas de réponse sur les routes publiques (18 sept. 2026, point 8 du plan)** : `apps/api/src/routes/public.ts` sérialise à travers `apps/api/src/schemas/public.ts`. Zod retire toute clé absente du schéma : une colonne ajoutée à `salons`, `services`, `staff` ou au retour d'une fonction SQL ne part plus toute seule, il faut l'ajouter au schéma, c'est-à-dire le décider. Ces schémas filtrent les CLÉS, ils ne jugent PAS les valeurs (pas de format de date, pas de liste fermée) : une valeur inattendue en base doit s'afficher, jamais transformer une page publique en 500. Un type de `@salondz/types` modifié sans son schéma casse le typecheck (`PublicSchemasMatchTypes`), et la liste des clés servies est figée par deux tests e2e. Nouveau champ public = type + schéma + liste du test.
- **Adresse du visiteur derrière les mandataires (20 sept. 2026, `apps/api/src/lib/proxy.ts`)** : il y a DEUX intermédiaires devant l'API — le réseau de diffusion (Cloudflare, plages publiques) puis le répartiteur interne de Render (10.x). On remonte `X-Forwarded-For` de la DROITE vers la gauche en sautant les mandataires de confiance et on s'arrête à la première adresse qui ne l'est pas : c'est le visiteur ; une entrée forgée par le client reste à gauche de la vraie. **Ne jamais revenir à un comptage de sauts** (`hop === 0`) : c'est ce que faisait le durcissement de septembre, et `req.ip` rendait l'adresse interne de Render — la limitation de débit par adresse retombait sur une poignée d'adresses partagées et le journal d'administration enregistrait 10.x. Vérifié en production en lisant les journaux Render.
- `SUPABASE_SECRET_KEY` et `DATABASE_URL` : API/scripts seulement, jamais dans web/mobile ni dans git (`.env*` ignoré, `.env.example` sans secret).
- L'API contourne la RLS (clé secrète) : chaque route protégée passe par `requireAuth` / `requireProfile` / `requireSalon` et vérifie l'appartenance (`salon_id`, `client_id`).
